# Project principles (read before every spec, prompt, or code change)

Team standing rules for the Diligent Track 2 sanctions-screening resolver. These override convenience.

1. **The job:** the system reviews an alert, makes a decision for every hit (SAME_ENTITY / DIFFERENT_ENTITY / REVIEW), and gives a reason for it.
2. **A bad decision is worse than no decision.** This is a principle, not just a scoring trick. When evidence does not settle it, answer REVIEW. Clear (DIFFERENT_ENTITY) only on an explicit SOP contradiction; confirm (SAME_ENTITY) only on explicit agreement with nothing contradicting. A transliteration or other-script match may support a confirmation or stop a name clearance. It must never create a clearance. If the names could be transliterations of each other, do not clear on `NAME_MISMATCH`. Uncertain or no decision label is also a good label to provide.
3. **Explainability is a primary target.** Every decision must be traceable: the reason code, the minimal cited evidence IDs, and the resolved customer_record_id, and the rule path that led there.
4. **Reasons must be precise.** 2–4 sentences, using this hit's own facts (names, DOBs, countries, dates, record IDs). No generic boilerplate, no hedging, no facts that were not used. Make sure you cite sources (grounding) for things found.
5. **Reproducibility is a primary target.** Diligent runs the system 5 times; decision and reason_code must be identical every run. Decisions are deterministic rules only; no model decides. Grok writes the reason wording, checked against the record. The output does not depend on the environment, the clock, or hash-seed order.
6. **The data is anomaly-detection-shaped.** Most hits are routine; true matches and hard cases are rare. Don't assume errors are common; mine the data carefully to understand the real patterns and surface useful signals before writing rules.
7. **Study the data deeply.** There is a lot of information across Alerts, Hits, Customers, Accounts, Onboarding, KYC checks, Notes and Search results. Mine it, and bring useful findings to the surface (documented in DATA_NOTES.md).
8. **Judge, Evaluate, Verify, in deterministic code.** Judge is the rules decision. Evaluate is an independent re-check of the name agreement and the date comparison. Verify checks that the reason code fits the decision and that every cited id exists in the files. Any disagreement downgrades a clearance or confirmation to `REVIEW`; it never creates one. The log is a side file (`*.verify.jsonl`), not the scored output. No model can change a decision or a reason code, and no environment variable can either.
9. **Hard constraints from the brief:** `system/run <data folder> <output file>`; Python 3 standard library or shell only; reads only that folder; under 30 minutes; never commit dev/ data or keys; last commit before the deadline is scored.
