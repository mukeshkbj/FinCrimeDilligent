# Project principles (read before every spec, prompt, or code change)

Team standing rules for the Diligent Track 2 sanctions-screening resolver. These override convenience.

1. **The job:** the system reviews an alert, makes a decision for every hit (SAME_ENTITY / DIFFERENT_ENTITY / REVIEW), and gives a reason for it.
2. **A bad decision is worse than no decision.** This is a principle, not just a scoring trick. When evidence does not settle it, answer REVIEW. Clear (DIFFERENT_ENTITY) only on an explicit SOP contradiction; confirm (SAME_ENTITY) only on explicit agreement with nothing contradicting.
3. **Explainability is a primary target.** Every decision must be traceable: the reason code, the minimal cited evidence IDs, and the resolved customer_record_id, and the rule path that led there.
4. **Reasons must be precise.** 2–4 sentences, using this hit's own facts (names, DOBs, countries, dates, record IDs). No generic boilerplate, no hedging, no facts that were not used.
5. **Reproducibility is a primary target.** Diligent runs the system 5 times; decision and reason_code must be identical every run. The decision path is deterministic code. A model may only supply a fact the rules could not parse, and only above the confidence threshold in rule 8. Grok may rephrase a reason and must not change the decision or the reason code. Temperature is 0, calls are cached by input hash, and any missing key or error uses the rules.
6. **The data is anomaly-detection-shaped.** Most hits are routine; true matches and hard cases are rare. Don't assume errors are common; mine the data carefully to understand the real patterns and surface useful signals before writing rules.
7. **Study the data deeply.** There is a lot of information across Alerts, Hits, Customers, Accounts, Onboarding, KYC checks, Notes and Search results. Mine it, and bring useful findings to the surface (documented in DATA_NOTES.md).
8. **Models.** The team uses Jev (TypeSafe AI, a System One decision model returning typed decisions with calibrated confidence), available on OpenRouter as `typesafe/jev-router`, so it is allowed in `system/run`. Use it only for narrow typed sub-questions the rules cannot settle (for example, which birth year an age sentence implies), never as a free-form decider. Act on its answer only above a confidence threshold. Clearing needs about 95% or better, the cost-matrix break-even of 60/63. Below that, keep the rule result (`REVIEW` when the missing fact was what would have settled the hit). Cache every call by input hash. Do not commit `dev/` data or keys. Verify identical outputs across 5 runs. Use `OPENROUTER_API_KEY` (`https://openrouter.ai/api/v1`) if it is set, otherwise `XAI_API_KEY` (`https://api.x.ai/v1`, OpenAI-compatible). With neither key, or on any error, fall back to the deterministic rules. On OpenRouter, typed questions use Jev and reasons use Grok (`x-ai/grok-4`). On the xAI API, Jev is not hosted, so the same typed JSON question and the reason wording both go to `grok-4`, still not as a free-form decider. Grok wording must not change the decision or the reason code.
9. **Hard constraints from the brief:** `system/run <data folder> <output file>`; Python 3 / Node stdlib or shell only; reads only that folder; a model only through OpenRouter or the xAI API as in rule 8; under 30 minutes; never commit dev/ data or keys; last commit before the deadline is scored.
